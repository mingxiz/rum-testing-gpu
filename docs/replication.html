Data paths are under final_data/. The synthetic tables are races: the time until a method holds a feasible point within 1 % of a certified optimum OPT, or within 1e-3 of it where OPT = 0. OPT is the objective of a feasible point whose certified bracket satisfies (UB − LB)/LB ≤ 1e-3.

3How a number is made

A fresh run writes to validation/results/; the table builders read that first and fall back to the stored records in replication/*/results/, so a clean clone rebuilds every table and a new run can be compared with the stored one.

4tab:density18–20 · the n = 18, 19, 20 grid

Four methods on 30 instances

BM-ADMM · Flow-CG · Flow-ADMMIP-CG
What
Ten densities per n: the pairwise design (every binary menu) and random menus at 0.025, 0.05, 0.1, 0.2, 0.3, 0.5, 0.7, 1 and 10 % of the n·2n−1 cells. Each entry is the time to the stop rule, in seconds.
Data
final_data/Numerical1/raw_data/n{18,19,20}_*.csv, one row per observed cell (menu bitmask, chosen alternative, p̂), and opt_ref.json with each cell's OPT and how it was certified.
Generator
data/gen_instances.py with seeded streams: gen_pairwise for the pairwise cells (p̂ seed 100), gen_medium for the others (menu seed 42, p̂ seed 100). A run regenerates its instance and refuses to start if its sha256 fingerprint differs from the stored one.
Reproduce
python replication/density_grid/reproduce.py: validation/run_paper_table.py starts validation/run_one.py once per (cell, solver), in a fresh process, on an idle GPU, one at a time.
Tables
python validation/make_lambda_tables.py writes paper/tables/tab_race_n{18,19,20}_l0.tex; python validation/make_final_results.py writes final_results/Numerical1/results_n{18,19,20}.csv, which also hold the λ = 0.5 and 1 races of the same cells.
Records
replication/density_grid/results/, one JSON per (cell, solver) with the full trajectory.
IP-CG
Cluster runs, replication/cgip/cluster_records/Numerical1/. At each n the pairwise cell finished; the other cells reached the 24 h cap, one n = 19 cell after running out of its 96 GB.

5tab:binary · binary menus, n = 25–35

Flow-CG at three points of the pairwise design

Flow-CGIP-CG · IP-H-CG
What
The pairwise design at n = 25, 27, 30, 32 and 35, at three points: outside the polytope (λ = 0), halfway (λ = 0.5) and inside it (λ = 1).
Data
final_data/Numerical2/raw_data/n<n>_sparse.csv (outside), _lam5 (halfway) and _lam10 (inside), with opt_ref.json.
Generator
The outside point is the pairwise instance (gen_pairwise, seed 100). The inside point is the uniform rule 1/|D| on the same menus (p_inside), the choice probabilities of the uniform mixture over all rankings. The halfway point is their average (gen_convex_path, λ = 0.5). OPT is 0 inside and certified by Flow-CG otherwise.
Reproduce
python validation/run_lambda_study.py --task 1: the certificates first (not timed), then each race through validation/feasibility/feas_one.py, in a fresh process on an idle GPU. A cell that already has a record in validation/results/lambda_study/ is skipped.
Tables
validation/make_lambda_tables.py writes paper/tables/tab_fes_pairwise_l{1,05,0}.tex (inside, halfway, outside); validation/make_final_results.py writes final_results/Numerical2/results_pairwise.csv.
Records
Outside: replication/feasibility_in_n/results/; inside and halfway: replication/convex_path/results/. n = 35 uses the two-layer uint24 pricing.
IP-CG, IP-H-CG
replication/cgip/cluster_records/Numerical2/. Each finished 14 of the 15 cells; the caps were 24 h for n ≤ 30 and 7 days for n = 32 and 35.

7tab:dsg · choice overload, n = 25

The Hong–Li test on the choice-overload data

Flow-CGIP-CG · IP-H-CG
What
The bootstrap test of RUM with B = 10,000 draws, on two specifications: the default alternative only (alt0, M = 301 cells) and all alternatives (full, M = 901).
Data
final_data/Application_DSR/raw_data/overload_data_25_long.csv, the pilot data of Dean et al. that the paper cites: 520 respondents, each answering 10 of the 301 menus (the 24 binary and 276 ternary menus with the default, and the full menu), n = 25 alternatives. Observed choices; no generator.

8tab:ai and the AI intervals · LLM choice, n = 18

The Hong–Li test on two LLM data sets

BM-ADMMIP-CG · IP-H-CG
What
The bootstrap test with B = 10,000 draws on 8,807 menus of 18 Apple Watch products, each put to the model 2,000 times (M = 73,492 cells), and the two-sided 95 % intervals for the distance that the text reports: [max(0, LB − c), UB + c], with c the 95 % quantile of ‖p̂b − p̂‖.
Data
final_data/Application_AI/raw_data/gpt6luna_noreason.npz and gmicloud.npz: one row per reply kept (replicate, menu, chosen) and the number of unparseable replies dropped. The raw jsonl replies (2.1 GB per data set) are not in the repository.

The table: python replication/empirical_ai_n18/run_bootstrap.py --model gpt6luna_noreason --no-ci (and --model gmicloud): the replicate as the respondent, B = 10,000 multinomial_reject draws, BM-ADMM with β = 5, abs 5e-4. Records
replication/empirical_ai_n18/results/bootstrap_ai_{gpt6luna_noreason,gmicloud}.json (the table) and ..._replies.json (the intervals). The results folder also holds the 100-reply sets and Flow-CG runs.

9IP-CG and IP-H-CG

The IP-CG and IP-H-CG numbers in the paper come from runs on a CPU cluster, made with an earlier version of the CGIP code: one run per node, 24 Gurobi threads, a cap of 24 h per run (7 days for binary menus with n = 32 and 35). Their result files are in replication/cgip/cluster_records/<experiment>/ as the cluster wrote them: a summary.csv per experiment and the per-run files it refers to. The final_results builders read them for the CGIP and CGIP-heur rows.

replication/cgip/run_cgip.py runs the same experiments with this release's solver, the RUM class with methods ip_cg and ip_cg_heur (Gurobi, CPU):

python replication/cgip/run_cgip.py race --set Numerical2 --key n25_sparse --method ip_cg --threads 24
python replication/cgip/run_cgip.py race --set Numerical3 --key n20_m28 --method ip_cg_heur --threads 24
python replication/cgip/run_cgip.py dsr --obs alt0 --method ip_cg --threads 24
python replication/cgip/run_cgip.py ai --model gpt6luna_noreason --method ip_cg_heur --threads 24
  • race takes a cell of final_data/<set>/opt_ref.json and stops once UB < OPT + max(10−2·OPT, 10−3), the paper's criterion, or at the cluster's cap (--cap-hours).
  • dsr and ai run rum.bootstrap with the class's defaults; they certify p̂ first and stop there if that does not close within --cert-hours (24). --model luna and deepseek select the 100-reply sets of the cluster's AI runs.
  • --restarts sets IP-H-CG's random-insertion restarts per pricing call (10, as in the paper). replication/cgip/README.md lists where these runs differ from the cluster's.

10Protocol and hardware

Every time in the paper follows one protocol, enforced by the runners:

  • one fresh process per (cell, solver), so nothing is carried from one run to the next;
  • the GPU idle before a timed run starts: at most 10 % utilisation and 4.5 GB in use, on two consecutive samples (validation/run_paper_table.py, wait_for_idle_gpu);
  • runs strictly sequential, never two at once;
  • no thread caps: every solver gets the whole machine, and the cores it used are recorded per run (avg_cores; the GPU solvers report about 1.0, one CPU thread plus the device).

Certificate runs are not timed in the paper, so they are not idle-gated.

11Running it again

python replication/density_grid/reproduce.py                   # tab:density18-20
python validation/run_lambda_study.py --task 1 2 3 --phase race   # tab:binary, tab:dense (and the grid at λ = 0.5, 1)
python validation/make_lambda_tables.py                        # paper/tables/*.tex from the newest records
python validation/make_final_results.py                        # final_results/Numerical1-3/
python validation/make_final_results_apps.py                   # final_results/Application_DSR, Application_AI
python replication/empirical_dsr_n25/run_bootstrap.py --obs alt0     # tab:dsg; and --obs full
python replication/empirical_ai_n18/run_bootstrap.py --model gpt6luna_noreason --no-ci     # tab:ai; and gmicloud
python replication/empirical_ai_n18/run_bootstrap.py --model gpt6luna_noreason --input replies --no-ci --distance-interval

The builders alone need no GPU: they rebuild every table from the stored records. The synthetic races take about 150 minutes of solver time in all, two hours of it the n = 35 halfway cell; the IP-CG and IP-H-CG experiments take days on a cluster.
