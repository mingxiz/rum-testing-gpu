# Instances, certified optima, stopping criterion, and the benchmark setup

## 1. Format

An instance is an array `cd` of shape (mp, 3): one row per observed (menu, alternative) cell —
`menu` an integer bitmask over alternatives 0..n−1 (bit *i* set ⇔ alternative *i* in the menu),
`alt` the alternative (0-based, a member of the menu), `phat` its observed choice probability
(sums to 1 within each menu). Every alternative of every sampled menu is observed. `mp` = number
of rows; `m2 = n·2^(n−1)` is the size of the (menu, alternative) slab; **density = mp / m2**.

## 2. Generation and seed control

Everything is regenerated from two integer seeds; nothing is stored that cannot be recomputed.

- **Random-menu family** (`gen_medium(n, mult, menu_seed=42, phat_seed=100)`), used for every row
  except pairwise:
  1. `rng = np.random.RandomState(menu_seed)`; draw integers uniformly in [0, 2^n) and keep a draw
     as a menu if it has at least two alternatives and has not been drawn before; stop as soon as
     the total number of cells Σ|menu| reaches mult·n(n−1). Menus are kept in draw order.
  2. `prng = np.random.RandomState(phat_seed)`; for each menu, in that order, draw |menu| uniforms
     and normalise them to the menu's choice probabilities, assigned to the menu's alternatives in
     increasing index order.
  The multiplier realises a density target d: mult = round(d·m2/(n(n−1))). Because m2 doubles
  with n, mult doubles with n at fixed density — that is why the cell names differ across n
  (`m2`/`m4`/`m8` are all the ≈0.025 % row).
- **Pairwise** (`gen_pairwise(n, phat_seed=100)`): every pair {i, j} with i < j, in lexicographic
  order, both alternatives observed; the two probabilities are normalised uniforms drawn from
  `RandomState(phat_seed)` in that order.
- The seeds enter only through numpy's legacy `RandomState` (MT19937), whose streams numpy
  guarantees to be identical across versions and platforms, so the instances are bit-for-bit the
  same on every machine. The draw order above is part of the definition: changing it changes the
  instance.
- Seeds are function arguments; the paper's instances are `menu_seed=42`, `phat_seed=100` for all
  30 cells. Different seeds give a different instance whose certified optimum is **not** in
  `opt_refs.json` — the fingerprint check below fails on purpose in that case.

## 3. The instance sets

Two sets of instances live here, generated by the same code and seeds; `opt_refs.json` holds a
certified OPT for every cell of both.

**(a) The race grid** — the n = 18–20 comparison of Section "Algorithm Comparison" (30 cells):
the same ten rows at n = 18, 19, 20 — pairwise, then nine density targets on a two-resolution
log grid: 0.025 / 0.05 / 0.1 / 0.2 % (sparse regime, ×2 steps), 0.3 / 0.5 / 0.7 / 1 % (crossover
regime, ≈×1.5 steps), 10 % (dense regime). `python gen_instances.py` writes them; `CELLS.md` and
`manifest.json` list every cell with mp, number of menus, realised density and OPT.

**(b) The feasibility set** — the feasibility study (13 cells, `python gen_instances.py --feas`;
`CELLS_FEAS.md`, `manifest_feas.json`):

| axis | cells | keys |
|---|---|---|
| pairwise design, growing n | n = 20, 25, 30, 32 (m_p = n(n−1) = 380 … 992) | `n20_sparse`, `n25_sparse`, `n30_sparse`, `n32_sparse` |
| pairwise design, extension | n = 33, 34, 35 (m_p = 1,056 … 1,190) | `n33_sparse`, `n34_sparse`, `n35_sparse` |
| n = 20, growing density | 1, 5, 10, 25, 50, 100 % of m₂ = 10,485,760 | `n20_d1pct`, `n20_m1380`, `n20_m2759`, `n20_m6899`, `n20_m13797`, `n20_dense` |

Three of these cells (`n20_sparse`, `n20_d1pct`, `n20_m2759`) are grid cells reused unchanged;
`n20_dense` is every menu of size ≥ 2 (`gen_dense`); the rest are new draws of the same
generators. n = 32 is the largest pairwise lattice the mask-indexed CGBFQP-GPU kernel holds on a
32 GB GPU; the extension cells n = 33–35 are solved with the two-layer pricing backend
(`pricing=stream_f32` up to n = 34, `stream_u16` at n = 35; `solver/flow_cg/MEMORY.md`),
same generator, same seeds, and their OPTs are certified by that backend.

**(c) Off-grid extras** — the `medium` K-parameter tuning cells (mult = 20 at n = 18, 19, 20) and
the n = 18 3 % cell (`n18_m231`), with certified OPTs, available with `--extras`; not part of any
table.

**(d) The convex-path set** (`python gen_instances.py --path`; `CELLS_PATH.md`, `manifest_path.json`) —
for n = 25, 30, 32 the pairwise instance p̂ is mixed with the uniform choice rule
p_inside(x|D) = 1/|D| on the same menus (0.5 / 0.5 on every pair, the choice probabilities of the
uniform mixture over all rankings, hence rationalizable and interior):

    p(λ) = λ · p_inside + (1 − λ) · p̂,   λ = k/10, k = 0, 1, …, 10.

Keys `n{n}_sparse_lam{k}`; k = 0 is the pairwise cell itself (same bytes, same reference
`n{n}_sparse`, re-run only as a consistency check), k = 10 is the uniform rule (distance 0). The
30 new references (3 n × k = 1..10) are certified with CGBFQP-GPU by `validation/feasibility/run_path.py`
to (OPT − LB)/LB ≤ 1e-3, or, once the point is inside the polytope and the distance is ~0, to the
absolute criterion OPT − LB ≤ 1e-5 (`criterion` field). Each record also carries `lambda` and
`base_key`. The distance falls with λ and reaches 0 before λ = 1 because the path enters the
polytope; the table in `validation/results/feasibility/PATH_REFS.md` shows where.

The same path on the **n = 20 density axis** (`python gen_instances.py --path20`; `CELLS_PATH20.md`,
`manifest_path20.json`): base cells = the six feasibility density cells (1, 5, 10, 25, 50, 100 %),
keys `n20_{cat}_lam{k}`, p_inside = 1/|D| on every observed cell of that design. Certified by
`validation/feasibility/run_path20.py` with the certifier of the base cell (CGBFQP-GPU at 1 %,
BM-ADMM at 5–100 %), relative 1e-3 or the absolute floor OPT − LB ≤ 1e-5 · OPT(λ = 0) of that
density once the distance is ~0; table `validation/results/feasibility/PATH20_REFS.md`.

## 4. Certified optimum (OPT) and fingerprint

`opt_refs.json` stores, per instance, the fields `opt`, `lb`, `gap`, `method`, `mp`, `n_cols`,
`wall_s`, `cd_hash`:

- `opt` is the objective value of a **feasible** point (a mixture of rankings), i.e. an upper
  bound on the true minimum; `lb` is a valid lower bound; **OPT in the paper is `ub`.** The
  true minimum lies in [`lb`, `ub`], within 0.1 % of it.
- `method`: 29 cells were certified by CGBFQP-GPU (its Frank–Wolfe lower bound, reduced-cost
  stop disabled, run until the gap closed); the n = 20, 10 % cell (mp = 1,048,422) by BM-ADMM with
  the explicit certificate (feasibility-pushed upper bound + Frank–Wolfe/Bellman–Ford lower
  bound), because column generation is too slow to close a 0.1 % gap on 1 M observations.
  `n_cols` / `wall_s` are the columns and time the certifying run took.
- `cd_hash`: the first 16 hex digits of the sha256 of the exact float64 (mp × 3) array the
  optimum was certified on. `gen_instances.py --check` regenerates every instance and verifies
  the fingerprints; `validation/run_one.py` refuses to time a solver on an instance whose
  fingerprint does not match its reference.

## 5. Objective and the paper's stopping criterion

Objective, in all solvers and in `opt`:

    dist(p̂) = min over the RUM polytope of  sqrt( Σ_rows ( x[menu, alt] − p̂[menu, alt] )² )

— the unweighted Euclidean distance on the observed cells.

**Race criterion (the tables of the paper).** A solver is timed until it holds a *feasible* point
x — a point of the RUM polytope, i.e. a mixture of rankings — with

    ( UB − OPT ) / OPT  ≤  1 %,        UB = dist objective at x,   OPT = `opt` from opt_refs.json.

The check runs every 50 iterations for the ADMMs and after every column for the column-generation
methods. For BM-ADMM and Flow-ADMM, whose iterates are infeasible at finite iteration counts,
the checked point is the feasibility push of the iterate (Möbius transform → flow-feasible rounding
→ zeta transform), so UB is always the objective of an exactly feasible point; column-generation
iterates are feasible by construction. Native stopping rules (reduced-cost thresholds, residual
tolerances) are disabled. In `solver.solve` this is `criterion="race", opt_ref=OPT, rel_tol=1e-2`.
Reported per run: wall time of the solve loop and the number of ADMM iterations (BM-ADMM,
Flow-ADMM) or generated columns (CGBFQP-GPU, CGIP, CGIP-heur).

## 6. Commands

```
python gen_instances.py            # race grid (30 cells): instances/*.csv.gz + manifest.json + CELLS.md
python gen_instances.py --feas     # feasibility set (10 cells): instances/*.csv.gz + manifest_feas.json + CELLS_FEAS.md
python gen_instances.py --check    # regenerate the race grid and verify fingerprints only (--feas --check for the study)
python gen_instances.py --extras   # also the four off-grid instances
python verify_solution.py --key n18_m39 --solution sol.json   # evaluate a mixture of rankings
python ../validation/run_paper_table.py                        # the paper's tables (see validation/)
```

## 7. Benchmark setup of the paper runs — resources available, resources used

| | available on the paper machine | used by one benchmark run |
|---|---|---|
| CPU | AMD Ryzen 9 9950X (Zen 5): 16 physical cores / 32 logical threads, 4.3 GHz base, 16 MB L2 + 64 MB L3 | GPU solvers: one software thread, ≤ 1 core (measured 0.9–1.0 cores busy for BM-ADMM and CGBFQP-GPU; 0.1–1.0 for Flow-ADMM, the low values being waits on spilled memory). CPU solvers (CGIP, CGIP-heur): as many cores as Gurobi takes; the count is measured and reported with each run |
| host RAM | 64 GB DDR5-6000, no memory limit imposed | ≤ 0.6 GB for BM-ADMM and CGBFQP-GPU at every cell; Flow-ADMM up to 35 GB when its device allocation spills to host (see below) |
| GPU | 1 × NVIDIA GeForce RTX 5090, 32 GB, 21,760 CUDA cores, driver 610.62, CUDA 13.3 | the whole device, one process at a time. Device-memory high-water: BM-ADMM 0.2–2.0 GB (n = 18–20), CGBFQP-GPU < 0.05 GB, Flow-ADMM ≈ 50·mp² bytes (29 GB at n = 18, 1 %; 52–64 GB, i.e. spilled, at mp ≈ 32–35 k; refused beyond) |
| software | Windows 11 Home (WDDM driver); Python 3.12.10, numpy 2.4.6, scipy 1.16.3 (OpenBLAS), numba, CuPy 14; Gurobi 13.0.2 for CGIP / CGIP-heur | every run in a fresh process, GPU verified idle before it starts (`validation/run_paper_table.py` waits for idle) |

All numbers above are from `replication/density_grid/results/*.json` (fields `avg_cores`, `peak_host_rss_mb`,
`gpu_pool_peak_gb`), measured on the runs that produced the paper's tables. Wall times on WDDM
fluctuate by about ±20 % for launch-bound workloads; iteration and column counts are
machine-independent.

**Fairness conventions.** No solver is restricted: no thread caps are imposed, every run has the
whole machine, and what a solver actually uses is measured and recorded rather than assumed. The
GPU solvers happen to use one CPU thread (their CPU-side linear algebra is too small for OpenBLAS
to multithread — measured, not configured); Gurobi is free to use all cores in the CPU runs, and
the tables report the cores it used. One-off preparation that is reused across solves of the same
design is reported separately from the solve loop: Flow-ADMM's Mhat/Schur build, Gurobi's
pricing-model build, BM-ADMM's optional β probe. Kernel compilation and butterfly calibration are
warmed up on a tiny instance before timing.

**Running the CPU solvers elsewhere.** So that "N cores" means N cores: allot N physical cores to
the process (Slurm `--cpus-per-task=N --hint=nomultithread`, or `taskset` on distinct physical
cores), set Gurobi as default parameter, run one
fresh process per cell, and report the measured `avg_cores` next to the setting (Gurobi typically
uses fewer threads than offered on these small IPs). Record the CPU model, physical and logical
core counts, RAM, Gurobi version, and the master-QP backend used.
