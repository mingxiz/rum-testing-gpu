RUM Distance Solvers

How far are observed choice probabilities p̂ from the random-utility polytope? The RUM class answers with a certified bracket lb ≤ dist ≤ ub from any of seven methods; given a known optimum, it runs the paper's timing race instead. This page maps how the pieces fit together, what each method does inside, and how to call it.

1The big picture

There are two ways into the engines, one per job. The RUM class certifies a distance: it checks the data, picks or checks the method, plans GPU memory, enforces max_time, and always returns a certified bracket. Your code and the paper's certificate drivers both go through it. solver.solve() runs the paper's timing race: one named method, until its upper bound is within 1 % of a known optimum. The class runs that same race when given opt (§9). Both reach the same seven engine functions, and the engines share one set of building blocks in solver/common.

2One call, step by step

from solver.rum_solver import RUM

rum = RUM(menu, alternative, choice_probability)   # one row per observed (menu, alternative)
rum = RUM.from_rows(cd, n)                         # the same from cd, the choice data: an (M, 3) array of rows
res = rum.calculate_distance()                     # automatic method, abs 1e-5 / rel 1e-4, 1 h
res = rum.calculate_distance(method="bm_admm", rel_tol=1e-3,
                             method_args={"check": 100}, max_time=600)
res.exit_flag, res.distance, res.lb, res.ub, res.p_fit
print(res)                                         # every field, one per line
res.to_dict()                                      # the fields as plain values, for json.dump
  • Singleton menus are taken out before solving (their probability must be 1) and added back as a constant c: lb = √(lb′² + c), ub = √(ub′² + c).
  • The geometry (menus and alternatives) is built once per RUM object and holds the caches: the Gurobi models of bm_qp, flow_qp and IP-CG, and Flow-ADMM's Mhat. A bootstrap loop passes p= per draw and reuses them.
  • max_time starts at the call. Setup counts: model builds, Mhat, kernel compilation. This matters mostly for the exact QPs and Flow-ADMM.

4Automatic choice

method=None calls choose_method(n, mp, weighted, profile). With a GPU it picks bm_admm or flow_cg, from n and the density (observed (menu, alternative) cells ÷ n·2n−1). Memory is the only thing that overrides the density rule. The thresholds live in defaults.AUTO["bm_admm_min_density"] = {11: 0.02, 14: 0.01, 18: 0.005}.

Why sparse designs go to flow_cg

A bm_admm iteration costs the same whatever the number of observations, and it needs few iterations when many cells are observed. flow_cg pays per observation and needs few columns when there are few. On sparse designs bm_admm is slow to certify, for two different reasons:

  • Small n, pairwise. The iterate and the lower bound are both within 1e-4 of the optimum after 450–2,000 iterations. The pushed upper bound needs 114,350 (n = 8) to 362,850 (n = 10) iterations. The push clips the iterate's negative Block–Marschak terms on the unobserved lattice, and ADMM removes those slowly.
  • DSR alt0 (n = 25, 301 observations). Here the iterate itself is far off: its lower bound is 0.99 after 10,000 iterations and 1.40 after 4 h, against a distance of 1.489.

A sharper upper bound was tried: the 500 heaviest rankings of the pushed flow, then the exact QP over them. It reaches the optimum early on the small pairwise designs, but only 1.95–2.9 on DSR, and at n = 14–17 it never beats the push at 0.5–2 %. It is not adopted: the density rule already sends every such design to flow_cg.

5The certificate

Every method ends with lb ≤ dist ≤ ub. The methods differ in where the two bounds come from.

6Storage formats

Each GPU method keeps its working values in one format, chosen per call with method_args={"dtype": …}. Without it, the class takes the most precise format that fits 90 % of the free GPU memory. The tolerance never lowers precision: a format that cannot reach the tolerance still runs, and the result's message says so. An explicit dtype that does not fit raises before solving, with the sizes.

Methoddtype you can passWithout dtypeWhat it stores
bm_admmfloat64, float32float64. When that does not fit (n ≥ 24 on 32 GB), auto takes flow_cg; an explicit bm_admm raises and names float32's sizethe ADMM state, 14 slabs of n·2n−1. float32 halves the memory, but its pushed ub stalls: n18_m39 is still 2.6 % above its lb after 120 s
flow_cgfloat32, uint24, uint16the first that fits: float32 (whole lattice, else two layers), then uint24, then uint16the pricing values. uint24 and uint16 are block-scaled integers: they save memory, not time (uint16 is 3–6 % slower per column)
flow_admmfloat32float32the ADMM state (its kernels are float32). Mhat and the Schur factor are always float64: in float32 the solve diverges

flow_cg's pricing is the layout only: "mask" (one value per subset, n ≤ 32) or "stream" (two live layers, rank-indexed). The old names stream_f32, stream_u24 and stream_u16 still work and set both. The result reports pricing and dtype separately, and info["pricing"] keeps the engine's backend name. The race (§9) keeps its own arguments.

The bounds are not a choice

Whatever the dtype, both bounds are float64 wherever a float64 form fits. bm_admm and flow_admm take the lower bound from the slab (§5). flow_cg's final lower bound takes the first of these that fits, once the pricing buffers are freed:

Not built, and why

  • Auto never picks a float32 BM-ADMM state. It does not certify: n18_m39 is still 2.6 % above its lb after 120 s, where float64 certifies rel 1e-4 in 22.5 s, and in 88 of 90 race cells the float32 leg stalled before 1 %. It would only matter at one n per card (24 on 32 GB, 26 on 141 GB), and flow_cg fits there.
  • No rounded-up float32 bound for n = 34. It would cover one n on one card (a 141 GB card does n = 34 in float64, two layers at a time).
  • No float64 pricing. With the final bound in float64, pricing precision only changes which column is picked: the master recomputes each column's reduced cost in float64. It would double the memory, at 1/64 of the single-precision rate on GeForce cards.
  • No float64 flow_admm state. It is never chosen automatically, and every kernel of its loop would need a float64 version.

How it was checked

  • The two-layer sweep's maximum equals the slab's longest path to 5e-16 at n = 3–26, and the two bounds at flow_cg's own points agree to 4e-16 (pairwise n = 8–26, random menus n = 8–14).
  • Its device memory equals the planner's formula (which includes 4 KiB for the memory pool's rounding). One bound on the pairwise design takes 0.03 s at n = 26, 0.63 s at n = 30, 2.9 s at n = 32 and 6.1 s at n = 33.
  • Through the class at n = 20, each bound form (the slab, and the other two forced) and each dtype: two layers equal the slab (the same 199 columns and ub, lb within 2e-16); stream float32 equals mask exactly; uint24 gives the same 199 columns; uint16 certifies in 197. The forced pricing-sweep form reports lb_rigorous=False with its note; bm_admm float32 and flow_admm run.
  • Against the float32 bound lowered by δ, on the pairwise design at rel 1e-3: the same columns and ub in every cell, a higher lower bound and about the same time:

7The seven methods

Each method can be called through the class (method="…", method_args={…}) or as its engine directly. Below, cd is the choice data the engines take: an (mp, 3) array with one row (menu, alternative, p̂) for each of the mp observed pairs, and geom is the class's geometry object. Any object with menu, alternative, num_alternatives and M works as geom, including the older class solver.rum.RUM.

bm_admm

GPUchosen automatically paper: BM-ADMM

ADMM on the Block–Marschak formulation, matrix-free on the GPU. The default for dense designs.

Variables
One value per (alternative i, menu S containing i): a slab of n·2n−1 entries, with i's block at i·2n−1 + compress(S∖{i}). The Block–Marschak terms are the superset Möbius transform of the slab.
One iteration
Five fused elementwise kernels, one prox launch over all menus, and the Möbius/eigen butterflies. The butterfly stage plan is measured on this GPU once per process. With use_graph the whole iteration replays as one CUDA graph (n ≤ 22).
Bounds
Every check iterations: push in float64 → UB. The best UB is kept, and p_fit is taken at that push. Every lb_every checks: the Frank–Wolfe LB, a float64 sweep on the GPU (1.3 ms at n = 20).
Memory
Measured peak plus 10 %: 1.1 × 145 B per slab entry in float64 with the graph, 141 B without. That is 1.6 GB at n = 20 and 13.9 GB at n = 23. At n = 24 it needs 29.1 GB, which does not fit, so the automatic choice takes flow_cg. float32 takes 1.1 × 92 B (82 B without the graph): 16.9 GB at n = 24.
Settings
beta=None (= 0.033·mp0.51), alpha=1.95, precond_p=√2, check=50, lb_every=1, dtype="auto" (= float64; float32 only when asked, §6), use_graph="auto" (n ≤ 22), max_iter=10**7

flow_cg

GPUchosen automatically paper: Flow-CG

Column generation over preference rankings: Bellman–Ford pricing on the GPU, the master QP on the CPU. The default for sparse designs, and for any n where bm_admm does not fit.

Problem
dist(p̂)² = the minimum over mixtures λ of ranking columns of ‖Vλ − p̂‖². A ranking's column is 1 on each observed row whose alternative that ranking picks from the menu.
One iteration
One column per iteration:
  1. Solve the master QP over the simplex. It is an active-set Cholesky on Q = V′V and h = V′p̂, kept up to date from packed column bitsets, so V is never formed.
  2. Read the residual off Q, h and λ.
  3. Price: the best ranking is a longest path through the subset lattice. With mask pricing that is one kernel per cardinality layer; for large n it is a streamed, rank-indexed sweep (stream_*).
  4. Test the gap.
  5. Add the column.
Bounds
UB = the mixture's distance, recomputed exactly in float64 by the class. During the solve, LB = √max(UB² − 2·fw_gap, 0) from the pricing sweep, a running max. The engine rounds p̂ to float32, so the class lowers that LB by δ = ‖p̂ − p̂float32‖ and asks the engine for abs_tol − 2δ. At the end the class replaces it with the float64 Frank–Wolfe bound at the mixture's point, on the GPU: from the slab up to n = 26 on 32 GB, two lattice layers at a time up to n = 33 (info["lb_dtype"], ["lb_layout"], ["lb_rigorous"]; §6).
Memory
GPU, mask pricing: 5·2n + 4·2n bytes up to n = 28 (layers stored), and 5·2n + 4·C(n, n/2) above that. That is 5.6 GB at n = 30 and 22 GB at n = 32; the two-layer pricers go further (float32 to n = 34, uint24 and uint16 to n = 35). Host: the Gram matrix, 8·K² bytes for K = max_iters + 2 columns.
Settings
dtype="auto" (the pricing values: float32 where it fits, then uint24, then uint16), pricing="auto" (the layout: mask where it fits, else stream; the old names stream_f32, stream_u24, stream_u16 still work), layers="auto", max_iters=4000 (columns)
Files

flow_admm

GPUnamed only paper: Flow-ADMM

ADMM on the arc-flow formulation, with a prestored dense mp × mp matrix. Never chosen automatically. It pays off when the same menus are solved many times, because the matrix is reused.

Problem
r is a unit flow from ∅ to the full set on the subset-lattice digraph: n·2n−1 arcs, in the same layout as bm_admm's slab. The constraints are A r = b and r ≥ 0. The choice probabilities are y = zeta(r)[obs], and the objective is ‖y − p̂‖².
Setup
Mhat = C H0−1 C′ (mp × mp, float64), plus the Cholesky factor of its Schur complement. Mhat depends only on the menus and on (beta2, beta3). The class keeps it on the RUM object (up to 1/8 of RAM), so later calls skip the build: on n18_m39, setup drops from 4.8 s to 0.7 s.
One iteration
float32 kernels: A / A′, the Woodbury solve with H0, and the zeta operators C / C′. The two penalties are rebalanced every 25 iterations (adaptive).
Bounds
Every check iterations: push r to an exactly feasible flow and apply zeta, both in float64 → UB, best kept. Every lb_every checks: the Frank–Wolfe sweep at zeta(r)[obs], in float64 on the GPU → LB.
Memory
Measured: 1.1 × (55 B per mp² + 82 B per slab entry) + 0.25 GB. It must fit 90 % of the free GPU memory, so it never spills to host memory. n20_d1pct would need 621 GB, so it is refused.
Settings
dtype="auto" (= float32, its only kernels), beta2=2.0, beta3=0.05, alpha=1.8, adaptive=True, check=50, lb_every=1, max_iter=10**7
Files

ip_cg

CPU + Gurobinamed only paper: IP-CG

Column generation with an exact integer-programming pricing step. Takes any weight matrix.

One iteration
One column per iteration:
  1. Solve the master QP over the current columns: the native active set, warm-started from the last support, or Gurobi's barrier.
  2. Compute the residual g = Ω(p̂ − Vλ).
  3. Price with the IP: find the ranking with the largest vr·g. There is one Gurobi MIP per geometry, and only its objective changes.
  4. Run the gap tests.
  5. Add the column.
Bounds
UB = the master's mixture. LB = from the IP's ObjBound. With strict=True, which the class sets, a column already in the master ends the run as "stalled" instead of being added again.
Settings
qp_backend="native", threads=None (Gurobi's default), max_iters=100000

9The race path

The paper's timing tables come from races. solver.solve(n, cd, method, opt_ref=OPT) runs one named method until its feasible upper bound is within 1 % of the certified optimum. It refuses criterion="cert" and method="auto", with a pointer to the class. Rerun with this code, the paper's race cells reproduce the stored iterations and upper bounds bit for bit (all but the two-hour n35_sparse_lam5 cell, which was not rerun).

The class runs the same race when given opt: rum.calculate_distance(method="flow_cg", opt=OPT) calls solver.solve() with run_one.py's arguments. On 11 cells (bm_admm n18_m39, n20_m138 at λ = 0, 0.5, 1 and n20_m1380; flow_cg n18_sparse at λ = 0 and 1, n20_m28 and n25_sparse; flow_admm n18_sparse and n18_m4) the two gave the same iterations and ub, bit for bit, and all 11 reached the target.

The stop rule. A race stops at the first check where (ub − opt)/opt ≤ 0.01, i.e. ub ≤ 1.01·opt. BM-ADMM and Flow-ADMM test the ratio every check iterations; Flow-CG tests ub ≤ 1.01·opt after every column, the same rule multiplied out. When opt = 0 (or nearly), the target is max(1.01·opt, floor): run_one.py and feas_one.py then pass opt = floor/1.01. IP-CG's race (solve_cgip_paper) tests a strict ub < 1.01·opt and has no race mode in the class; replication/cgip/run_cgip.py applies the paper's stop rule to IP-CG and IP-H-CG through the class's session (below=) instead.
